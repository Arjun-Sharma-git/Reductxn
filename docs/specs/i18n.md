# Spec - Localization and locale-safe money

**Owner:** frontend reviewer · **Module:** `apps/web` (`shared/i18n`, `shared/money`) ·
**Related:** ADR 0014; RULEs F10, F11, F12, B20

## 1. Locale set

| Locale | Currency pairing | Plural categories | Direction | Notes |
|---|---|---|---|---|
| `en` | `USD`, `INR` (en-IN) | one, other | LTR | Source of truth catalog |
| `hi` | `INR` | one, other | LTR | Devanagari numerals optional; `latn` default |
| `ru` | `RUB` | **one, few, many, other** | LTR | Three plural forms, not two |
| `ja` | `JPY` | other only | LTR | No plural distinction at all |
| `ar`, `he` | reserved | - | **RTL** | Not launched; layout and animations must already allow it |

The plural column is the whole argument for ICU. English has two forms, Russian has four, Japanese
has one. Any string built by concatenating a number and a noun is wrong in at least one launch locale.

## 2. Catalog layout

```
apps/web/locales/
  en/{common,obligations,netting,settlement,tax,errors}.json   # source of truth
  hi/...  ru/...  ja/...
  _meta.json                                                   # per-locale review state
```

Keys are namespaced by feature. A catalog entry is a flat ICU message; nesting is only for grouping.

```jsonc
// en/obligations.json
{
  "obligations.countMembers": "{count, plural, one {# member} other {# members}}",
  "obligations.recorded": "Recorded {amount} to {creditor}",
  "obligations.settleInDifferentCurrency": "Settle in {currency} at {rate}"
}

// ru/obligations.json   -- four categories, not two
{
  "obligations.countMembers":
    "{count, plural, one {# участник} few {# участника} many {# участников} other {# участника}}"
}

// hi/obligations.json
{
  "obligations.countMembers": "{count, plural, one {# सदस्य} other {# सदस्यों}}"
}

// ja/obligations.json   -- one form
{
  "obligations.countMembers": "{count, plural, other {#人}}"
}
```

The two-digit `#` offsets and the `{amount}` interpolations are ICU, not template literals, so a
translator can reorder them. Reordering matters: the position of a currency amount differs by locale.

### 2.1 What is never translated

- **User-authored content**, such as an obligation `memo`. It is stored and rendered exactly as
  written, is not parsed for meaning, and is not used to derive a code. Two members who share a group
  but not a language will see each other's memos in the language they were typed.
- **Currency codes** (`INR`, `JPY`) and other ISO identifiers. `INR` is `INR` in every locale.
- **Generated clients, log lines and error `title`/`detail`.** Developer-facing, English only.

This is worth stating because "translate everything" is a tempting rule, and it produces a bug where a
user's own note appears rewritten in a language they did not write it in.

## 3. Locale resolution

1. authenticated user preference (stored on the user record)
2. the URL (`?lang=` or route segment) - **part of page identity**
3. `Accept-Language`
4. `en`

The resolved locale is reflected in the URL so a shared link opens in the language the sharer saw.
Switching language updates the URL and the user preference, in that order.

## 4. Money formatting: the P1 boundary

**RULE F11** - formatting goes through `shared/money`. Never a raw `Intl.NumberFormat` applied to a
JavaScript `number` amount, because that reintroduces the floating-point path P1 forbids.

The approach: take the digits from the exact `long` (via `Currency.format`, which never divides), and
take symbols, placement, grouping and the decimal separator from
`Intl.NumberFormat(locale, ...).formatToParts`. Digits are then substituted into the parts.

**Worked example.** `amountMinor = 123456789`, `INR`, exponent 2. Exact digits: `1234567.89`.

| Locale | Rendered | What changed |
|---|---|---|
| `en-IN` | `₹12,34,567.89` | **Lakh/crore grouping**: 2 digits after the first group |
| `en-US` | `₹1,234,567.89` | Thousands grouping |
| `ru` | `1 234 567,89 ₹` | Space grouping, comma decimal, symbol after |
| `ja` | `₹1,234,567.89` | Thousands grouping |

Every one of those is the same integer `123456789`. The grouping is the only difference, and it is
the reason this cannot be a `toLocaleString(amount / 100)` call.

**Zero-exponent case.** `amountMinor = 123457`, `JPY`, exponent 0. Exact digits: `123457`. Rendered
`ja`: `￥123,457`. No decimal separator is inserted, because the currency's exponent is data
(`Currency.minorUnitExponent`), not a formatting guess.

## 5. Amount input

**RULE F12** - input is parsed to integer minor units. Never `parseFloat`.

```
"12,34,567.89"  (en-IN)  ->  123456789
"1 234 567,89"  (ru)     ->  123456789
"123457"        (ja,JPY) ->  123457
"1.2.3"                  ->  rejected: amount.unparseable
"1.2345678"     (INR)    ->  rejected: amount.too_many_decimals
```

Parsing strips grouping separators using the locale's separators, locates the decimal separator,
then builds minor units by string manipulation and integer arithmetic. Over-precise input is
**rejected, not truncated**: silently dropping a digit from a money amount is the exact failure class
P1 exists to prevent.

## 6. Errors: codes, never prose

**RULE B20** - the API never returns localized prose. Problem responses carry a stable `code` and
structured `params`; the client localizes from the `errors` namespace.

```jsonc
// server returns
{ "type": "https://reductxn.io/problems/currency-mismatch",
  "title": "Currency mismatch",             // English only, for developers and logs
  "status": 422,
  "code": "ledger.currency_mismatch",
  "params": { "expected": "INR", "actual": "JPY" } }

// client renders, per locale
// en: "This group settles in INR, but the amount is in JPY."
// ru: "Эта группа рассчитывается в INR, но сумма указана в JPY."
```

Consequences: adding a language never requires a backend release; error text is assertable in tests
by code rather than by string; and logs stay in one language.

Every code the API can emit must exist in `en/errors.json`. CI enforces the reverse direction too:
an `errors` key with no matching server code fails the build, so dead codes are removed.

For that check to be possible at all, the server's codes have to be **enumerable**. They are: every
`DomainError` declares its code as a `public static final String CODE`, so the set can be collected
rather than maintained by hand, and `DomainErrorCodeTest` holds them to the format - lower case,
dot-separated, namespaced by the owning module (`ledger.currency_mismatch`, `fx.rate_stale`).

## 7. Timezone

Each group has a `settlementTimezone` (IANA zone), defaulting to the creator's zone. It is used for:

- the cycle boundary (when a cycle closes and which obligations belong to it),
- the effective date of a tax rule,
- the "as of" rendering in reports.

Members see timestamps in their own locale and zone, but **the boundary belongs to the group**, so
every member agrees which cycle an obligation falls into. Changing the group timezone is forward-only
from a stated instant, because retroactive change would rewrite cycle membership.

## 8. Translation pipeline

1. `en` is the source of truth and is edited by developers in the same pull request as the feature.
2. CI fails on a **missing key** relative to `en`, and on an **unused key**.
3. CI fails on a **user-facing literal** in a component (**RULE F10**) unless it carries an explicit
   `// i18n-ignore: <reason>` marker for things like brand names.
4. Machine translation is allowed to seed a locale, must be marked in `_meta.json` as
   `"reviewed": false`, and the app **refuses to render an unreviewed locale** on money-moving and
   approval screens, falling back to `en` with a visible notice.
5. A human review flips the flag. This is a financial product; an MT error in "you will pay" is not a
   cosmetic defect.

## 9. Direction

Launch locales are LTR, but layout uses CSS logical properties (`margin-inline-start`, not
`margin-left`) and GSAP animations read direction from a token in `shared/gsap/presets.ts`. Adding an
RTL locale must not mean rewriting animations, margins and icon mirroring.

## 10. Properties and gates

| # | Property / gate | Status |
|---|---|---|
| I1 | Every `en` key exists in every shipped locale, or the locale is flagged incomplete | **Implemented.** `apps/web/tools/check-catalogs.mjs` fails on a missing key for a locale that does not carry `"complete": false` in `locales/_meta.json`, and reports it for one that does. `ru` is shipped that way on purpose: a partial seed that reads as missing translation (per-key fallback to English) rather than as a broken screen |
| I2 | No unused keys in `en` | **Implemented** in the same check. A key built from data - `` t(`netting.direction.${direction}`) `` - is matched by its literal prefix, which is the one looseness in it and is stated in the tool |
| I3 | Every server error `code` has an `errors` entry, and every `errors` entry has a server code | **Implemented, in both directions**, and the server's codes are *collected* from the Java sources rather than listed by hand - which is only possible because every `DomainError` declares its code as a constant (`DomainErrorCodeTest` holds them to the format). `client.*` and `amount.*` are carved out as client-owned namespaces; an entry there has no server constant to match by definition |
| I4 | Round trip: `parseAmount(formatAmount(minor, locale), locale) == minor` for all locales and generated amounts | **Implemented.** A Vitest property test over `en-IN`, `en-US`, `ru` and `ja`, with a deterministic generator (fixed seeds plus a few hundred values) rather than a property-testing library - the reasons are in ADR 0028 |
| I5 | Formatting never changes the digits | **Implemented** in the same test, as "the digits of the output are exactly the digits of the integer". This is the one that caught three real defects: ungrouped amounts, a wrong secondary group size for `en-IN`, and a digit-mapping table that turned a grouping space into a zero |
| I6 | No `double`/`float` in the formatting or parsing path | **Implemented as lint**: `Number.parseFloat` is a `no-restricted-properties` error everywhere, `Intl.NumberFormat` is one outside `shared/money` and `shared/i18n`, and dividing by a hundred is a `no-restricted-syntax` error. The Java side has the same rule as a Gradle task |
| I7 | Plural forms are present for every category the locale requires | **Implemented** in the catalog check, with the categories read from `Intl.PluralRules` rather than from a table: Russian's four forms are a fact about Russian, and a table in the tool would be a second, ageing copy of it |

Two gates are worth naming because they are *not* here. **RULE F10's literal check is ESLint**, not this tool
(`no-restricted-syntax` on JSX text), and the one deliberate exception is the product's own name, which lives in
`shared/config` because a brand is configuration rather than copy. And **none of it runs in CI**: there is no
pipeline configuration in this repository, so the checks run from `pnpm check` and `pnpm e2e`.

I4 and I5 are the two that matter most. I5 is the one that catches a well-intentioned
`toLocaleString(amount / 100)` refactor, which would pass I4 for most inputs and be wrong for large
ones.

## 11. Open questions

- **Where the locale lives: answered for the URL (ADR 0028).** It is a query parameter (`?lang=ru`) rather than a
  path segment, because it keeps the route tree about the domain - `/groups/{groupId}/netting` reads the same in
  every language - and keeps the locale out of every link a screen builds. Still open: **the user's stored
  preference**, which is step one of the resolution order and needs identity to exist.
- Whether Devanagari (`deva`) numerals should be offered for `hi`, or `latn` only. Default is `latn`,
  since financial UIs commonly use Latin digits in India.
- How a *reviewed* flag is flipped in practice: today it is a hand-edited key in `_meta.json`, which is honest but
  has no trail. A translation pipeline would want the reviewer's identity and the revision reviewed.
- Whether the locale should live in the path (`/ru/groups/...`) or a query parameter, and how that
  interacts with the TanStack Router file-based route tree.
- How to surface "this locale is machine-translated" without undermining trust in the product.
- Whether the `errors` namespace should be split per feature to keep bundles small.
